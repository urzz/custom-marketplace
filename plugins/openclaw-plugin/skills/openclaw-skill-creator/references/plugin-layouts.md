# OpenClaw skill 布局选择

本文说明什么时候应该把目标产物设计成 **独立 skill**，什么时候才需要做成 **插件携带型 skill**。

## 1. 独立 skill

### 典型结构

```text
my-skill/
├── SKILL.md
├── references/
│   └── validation.md
└── scripts/
    └── validate.py
```

### 何时优先选择
默认优先选这种形态，尤其是：
- 只做一个 skill
- 先验证能力是否成立
- 不需要和其他 skill 一起分发
- 没有共享脚本、共享资源或统一插件治理需求

### 优点
- 结构最轻
- 修改成本低
- 更适合首版探索
- 用户更容易理解哪些内容属于 skill 本体

### 风险
- 如果后续要扩展成多 skill 体系，可能还要再做一次分层整理

但对首版来说，这通常是可以接受的。

---

## 2. 插件携带型 skill

### 典型结构

```text
my-plugin/
├── .claude-plugin/
│   └── plugin.json
└── skills/
    ├── skill-a/
    │   └── SKILL.md
    └── skill-b/
        └── SKILL.md
```

### 何时考虑
只有在以下需求比较明确时再选：
- 需要统一发布多个相关 skill
- 需要共享元数据、共享资源或统一版本管理
- 组织上本来就按插件分发
- 用户已经明确要求“做成插件形态”

### 优点
- 适合多 skill 管理
- 适合统一打包、统一版本化
- 能承载更明确的分发边界

### 风险
- 首版复杂度更高
- 用户可能还没验证单个 skill 是否值得继续投入
- 容易把“分发方式”误当成“能力本身”来设计

---

## 3. 默认建议

如果用户没有明确要求，默认建议：

1. 先做 **独立 skill**
2. 如正文变长，再加 `references/`
3. 如出现可复用的确定性辅助逻辑，再加 `scripts/`
4. 真正出现多 skill / 共享资源 / 统一分发需求时，再升级到插件携带型

也就是说：
- **独立 skill** 是默认起点
- **插件携带型** 是规模化后的组织方式

---

## 4. 对话中可直接使用的判断问题

如果你需要帮用户做选择，可以直接问：

1. 你现在是只要一个 skill，还是准备做一组相关 skill？
2. 这些 skill 之间会不会共享资源、模板或脚本？
3. 你当前最重要的是先验证能力，还是先确定分发结构？

一般来说，只要第 1 个问题的答案还是“先做一个试试”，就优先建议独立 skill。

---

## 5. 快速判断口诀

- **先验证能力，用独立 skill**
- **开始成体系，再考虑插件**

默认不要为了“看起来完整”而一上来就做插件形态。
