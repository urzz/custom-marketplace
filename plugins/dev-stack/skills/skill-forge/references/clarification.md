# 需求澄清与第一性原理

在 CREATE 和 MODIFY 写入 Spec 前使用本协议。Focused 是默认深度；Grill 是更深的 Discovery，不是风险等级、状态机或 artifact 类型。

## Focused

默认使用 Focused：

- 只询问会改变目标行为、触发边界、文件范围、权限、副作用或验收标准的问题。
- 仓库规则、源码、review 文档或用户上下文已经回答的问题不再询问。
- 适用于目标明确的 MODIFY、已有完整 review 结论的优化，以及边界清晰的 CREATE。
- 若所有关键信息已经存在，直接综合第一性原理，不为了完成问卷制造问题。

## Grill

满足任一条件时使用 Grill：

- 用户明确说 `grill me`、要求深度追问或苏格拉底式澄清；
- CREATE 的核心用户和真实问题不明确；
- 用户给出的是解决方案而不是问题；
- 目标使用“更智能”“更灵活”“更健壮”等不可观察表述；
- Should Trigger / Should Not Trigger 无法写成具体请求；
- 存在会显著改变架构、权限、副作用或验收方式的未决选择。

Grill 通过更多对话轮次获得更可靠的 Spec，但仍遵守一次一个问题和停止条件。不要把它实现为固定问卷或新的运行路径。

## 追问协议

1. 一次只问一个关键问题。
2. 先指出当前假设、证据缺口或矛盾，再提出问题。
3. 在证据充分时给出推荐答案和理由，允许用户覆盖推荐。
4. 优先要求真实请求、输入、输出和失败案例，不接受抽象形容词作为验收条件。
5. 区分事实、推断、假设和必须由用户决定的事项。
6. 不重复询问能够从仓库或现有文档确定的内容。
7. 不为了“完整”而追问；每个问题都必须可能改变 Spec。
8. 发现用户请求的是手段时，追问其想改变的可观察结果。
9. 发现 Skill 不是最小合适载体时，说明更合适的 script、plugin agent、仓库规则或一次性任务，并请求用户决定。

推荐问题格式：

```markdown
当前假设：[目前从上下文得到的判断]

问题：[本轮唯一需要用户决定的问题]

建议：[推荐选择及理由]
```

## 第一性原理维度

按需覆盖，不要求逐项提问：

1. 根本问题是什么，为什么现有宿主通用能力不足？
2. 真正需要的是 Skill、script、plugin agent、普通仓库规则，还是一次性任务？
3. 最小必要能力是什么？
4. 谁会使用，输入和输出分别是什么？
5. 哪些请求应该触发，哪些相邻请求绝不能触发？
6. 哪些现有行为和边界必须保持不变？
7. 是否涉及写文件、网络、发布、权限扩大或不可逆副作用？
8. 如何通过具体场景证明 Skill 有效？
9. 哪些内容明确不做？

## CREATE 与 MODIFY

CREATE 重点确认：

- 用户真正要解决的问题；
- 目标平台（Claude Code、Codex 或双平台）、目标用户与使用场景；
- 是否确实需要 Skill；
- 最小能力、触发边界、输出和副作用；
- supporting resources 是否真正需要复用。

MODIFY 重点确认：

- 当前行为、失败证据和复现方式；
- 根因而不是表面症状；
- 必须保留的已有行为；
- 最小变更边界；
- 是否影响 description、workflow、scripts、agents 或发布合同。

## 停止条件

同时满足以下条件后停止追问：

- 根本问题和目标用户明确；
- 最小必要能力明确；
- Should Trigger / Should Not Trigger 有具体例子；
- 输入、输出和副作用明确；
- 不可变约束与非目标明确；
- 验收标准可观察；
- 不再存在会改变范围、架构、权限或验证方式的未决选择。

未满足停止条件时不要写 Spec。满足后不要继续为了形式完整而追问。

## 综合输出

写 Spec 前在对话中输出：

```markdown
## First Principles Synthesis

- 根本问题：
- 最小必要能力：
- 不可变约束：
- 关键假设：
- 明确非目标：
```

该综合不是独立 artifact，不增加单独确认 Gate。把内容直接写入 `spec.md`，由 Spec 确认统一批准。
